# DeepSeek Coding Delegation

Use the queen where its judgment most affects quality: intent, acceptance criteria, architecture and consequential tradeoffs, uncertain failure diagnosis, risk-focused review and final acceptance. Bounded labor can go to a Codex-native `gpt-5.6-luna` subagent or to the plugin's persistent DeepSeek/GLM OpenCode worker. The objective is to preserve the queen’s capability while offloading labor, not to minimize queen involvement at the expense of quality. Combined tokens and latency can increase; do not promise measured savings without a comparable baseline.

## Divide judgment from labor

- Queen: decide what is correct, which constraints matter, consequential design choices and whether the evidence supports acceptance. Spend attention on unresolved uncertainty and risky changes.
- Delegate: search files, trace calls, inventory dependencies, compare existing patterns, edit code and docs, add/run relevant tests, fix known failures, reduce logs and prepare a diff/evidence summary. Delegate these supporting tasks even when their output is investigation rather than a patch.
- For a blocking design/business choice, ask the worker for the decision needed, options, tradeoffs and its recommendation, with source paths or test evidence. The queen decides; the worker resumes. Do not interrupt the queen for ordinary implementation choices already covered by scope.

## Select the worker lane and model

- Honor an explicit lane or model choice. “Codex 内置 Luna / 原生 Luna / GPT-5.6 Luna” selects the native `gpt-5.6-luna` subagent lane. “OpenCode Go / Go 套餐”, “官方 DeepSeek / DeepSeek API”, DeepSeek, or GLM selects the external OpenCode worker lane. Never silently switch lanes after unavailability, authentication, quota, or model errors.
- Treat a fleet-scoped instruction such as “所有工蜂都用 5.6 Luna” or “本次全部 worker 使用 GLM 5.3 Flash” as the model/lane choice for every new delegate in the stated scope. It overrides automatic lane preferences but not safety, review or capability boundaries. Existing workers keep the model they were created with; create replacement workers when the fleet instruction requires another model. Unless the user says “以后 / 全局 / 所有新执行者”, “所有工蜂” means the current coding task or current Codex thread, not a machine-wide preference.
- For native Luna, use Codex's native subagent capability with `model="gpt-5.6-luna"`. When the user does not explicitly specify an effort, pass `reasoning_effort="max"` in the spawn call; do not rely on the host default. Do not call any `ds_*` tool, start OpenCode, pass plugin `provider` fields, or read/forward external provider credentials. Native availability comes from the current Codex host; report an unsupported model/effort combination rather than substituting another model. Retain the native agent identity and use the host's native message/follow-up, wait and interrupt controls for task-scoped multi-turn corrections. This plugin cannot persist a native Luna default through `ds_model_defaults`; a Luna choice is scoped to the requested work or current thread preference, and changing its model requires a new subagent.
- Map native “推理最大 / 最高 / 拉满 / max” to `reasoning_effort="max"`, “高 / high” to `high`, “中 / medium” to `medium`, and “低 / low” to `low`. If the user explicitly asks for “默认档位 / 自动”, omit `reasoning_effort` for that request; this is an intentional override and is distinct from leaving the effort unspecified. Never silently lower an unsupported effort.
- The remaining model-selection rules in this section apply only to the external OpenCode worker lane.

- Accept ordinary language. “OpenCode Go / Go 套餐” selects `opencode-go`; “GLM 5.3 Flash” selects `glm-5.3-flash`; “官方 DeepSeek / DeepSeek API” selects `deepseek`, with Flash model `deepseek-flash`. Preserve other explicitly named model IDs and validate the catalog.
- Map “推理最大 / 最高 / 拉满 / max” to `variant="max"`, “高 / high” to `high`, “低 / low” to `low`, and “默认档位 / 自动” to `null`. When an external provider or model is explicitly selected without a variant, resolve the omitted variant to `max`; only an explicitly supplied `variant=null` asks the runtime to choose. `high` does not satisfy a request for maximum reasoning. Never silently lower an unsupported variant.
- The chosen interaction convention is that a standalone model/effort-setting request, such as “使用 OpenCode Go 里面的 GLM 5.3 Flash，推理开到最大”, saves the machine default through `ds_model_defaults(action="set", ...)`. “以后 / 全局 / 所有新执行者” also means persistent. Preserve scope the user already established. “这次 / 当前任务” or a model choice attached to a specific coding task overrides that task's new workers only: pass the full selection on their spawns without saving global defaults.
- After setting an external default, report the resolved provider, model, variant and scope briefly. It covers this plugin's subsequently created OpenCode workers on this machine, including future Codex tasks; existing workers keep their selection. It does not change the Codex controller model or native Luna. Use `action="get"` for “查看当前 OpenCode Worker 默认模型” and `action="reset"` for “恢复插件原来的默认模型”.
- With no explicit task selection, let check/spawn inherit the saved machine default rather than passing hardcoded model arguments. With no saved preference, the built-in default remains `opencode-go/deepseek-v4.1-flash` with `max`; an explicit provider/model switch that omits `variant` also resolves to `max`. A saved default for the same provider/model pair still wins, including a saved `null`; an explicit `variant` or `variant=null` always wins over saved settings. Call `ds_check` with the same overrides and workspace before first use of that configuration; its `ok` means configured and listed, not verified credentials or inference.
- Follow-ups, queued messages and forks preserve their own stored selection, including after a global-default change. Start a new worker when the task explicitly changes model. Never silently switch provider or model after a failure or quota limit.
- Both external providers use OpenCode as the agent runtime; the official provider uses separate DeepSeek API credentials. Read [worker lane, model selection and setup](references/model-selection.md) for native/external boundaries, precedence, authentication, CLI examples or missing models. Keep keys out of prompts and manifests.

## Route and delegate

Choose the route from how much judgment, risk, and exploration/verification burden the task carries — not from line counts or file counts. This is a decision guide for Codex’s situational judgment, not an automatic classifier, and an explicit user request to delegate or to stay direct overrides it.

- **Small (direct):** a known, clearly understood change that takes a few minutes and needs neither broad discovery nor risky design. Handle it in Codex directly; briefing and reviewing a worker would cost more than the edit. Report the route as direct.
- **Medium (prefer delegation):** mechanical implementation, or a larger amount of testing, with clear and objective acceptance criteria. Prefer native `gpt-5.6-luna` for bounded, low-risk subtasks when the host supports it. Task-scoped multi-turn corrections, queued input and worktree isolation do not by themselves require OpenCode: use the host's native follow-up/queue controls and managed worktree support when available, or let Codex prepare a dedicated Git worktree and give Luna that exact working directory. Prefer the DeepSeek/GLM OpenCode lane when the user selects it or the task materially needs cross-Codex-task/restart discovery, controller-persisted agent state, OpenCode context forks, external-provider usage accounting, or persisted `task_spec` verification.
- **Large or high-risk (delegated labor, queen-owned design):** state machines, concurrency, permissions, transactions, migrations, or changes where a wrong invariant, interface or failure semantic is expensive. Bounded labor may go to either lane, but Codex must first decide the design, interface, data flow, invariants, failure semantics and acceptance examples; then Codex reviews the actual diff and runs independent verification. Never accept any delegate’s self-report or passing self-tests as acceptance.
- Hand off a coherent behavior or investigation with acceptance criteria, rather than one function or tool command per turn.
- Prefer one lane and one delegate for a coherent task. Keep Luna prompts bounded and reuse an applicable native subagent only while its task and selected model remain coherent. Reuse a persistent OpenCode worker for related corrections; use a fresh worker for unrelated tasks.
- Before spawning, read applicable repository instructions and the critical call chain. Codex must decide the interface, data flow, invariants, failure behavior and acceptance examples that determine correctness. Leave routine implementation and broader discovery to the worker. Do not substitute a vague task restatement for a design, or prewrite every implementation detail.
- For the OpenCode lane, send a `task_spec` with the design decisions, observable acceptance criteria and exact checks selected by Codex. Keep it grounded in existing contracts; do not add speculative constraints. For an unfamiliar subsystem, first request a bounded discovery report from the same worker, then resolve the consequential decisions before implementation.
- For the OpenCode lane, use concrete `scope_paths`, task-relevant `required_reads` (named sections for large files), and a few non-secret `critical_constraints`. Send paths and observable requirements, not full source files or conversation history. Prefer `workspace_mode="worktree"` for work starting from HEAD; use `current` when uncommitted changes are required, after checking status and protecting unrelated edits.
- For native Luna isolation, prefer a host-native worktree/environment option when the active subagent interface exposes one. Otherwise Codex may prepare a dedicated Git worktree before spawning and explicitly constrain the Luna worker to that absolute working directory. Follow repository Git/worktree rules, start from the intended committed state, avoid assigning overlapping files to parallel workers, preserve reviewed changes before cleanup, and never imply that a worktree contains uncommitted source changes. When the task depends on current uncommitted edits, use the current workspace with non-overlapping writes or keep the work serial rather than silently using a stale worktree. Do not create a separate user-visible Codex task merely to emulate a hidden worker unless the user explicitly asks for a new task.

## Keep the queen loop small

### Native Luna lane

1. Select the workspace first. Use the current workspace for serial work that needs uncommitted changes. For independent work from committed state, use a host-managed worktree when exposed or create a dedicated Git worktree and include its exact path and write boundary in the task.
2. Use the host-native subagent tool (`spawn_agent` when available) with `model="gpt-5.6-luna"`, `reasoning_effort="max"` unless the user explicitly selected another effort or explicitly requested the host default, and a bounded objective, scope, design decisions and observable acceptance criteria. This is Skill-level orchestration, not an MCP plugin call. Do not send it provider credentials or use any `ds_*` tool.
3. Retain the agent identity. Use the native message or follow-up mechanism to queue a correction while it is running or resume the same idle agent for a coherent next turn; use native wait and interrupt controls instead of spawning a replacement merely because another turn is needed. These guarantees are scoped to the current Codex task unless the active host explicitly documents recovery beyond it.
4. Review its actual filesystem changes and relevant surrounding code; its final report is not acceptance. Run independent checks selected by Codex. After two unsuccessful review correction rounds, stop the worker and take over. Model changes still require a new subagent.
5. When Codex created a dedicated worktree, preserve or apply the reviewed patch before removing it. Remove only the exact task worktree after confirming no useful change remains solely there.

### OpenCode worker lane

1. Check prerequisites once per environment and selected model configuration. Spawn with the objective, allowed modules, instruction routing and `task_spec`. Ask the worker to implement, self-test and fix ordinary failures continuously before returning one concise handoff. It must escalate a contradictory design, missing consequential decision or out-of-scope requirement rather than guessing.
2. Keep the agent ID, worktree, cursor and instruction manifest. Use `ds_wait_agent(return_on="actionable", timeout_ms=55000)` with the latest cursor. Ordinary timeouts require another bounded wait, not a new diagnosis or transcript replay. Handle real attention events within existing authorization. The host still has a 65-second tool timeout: this workflow does not promise background completion notifications or zero polling.
3. Once the worker is idle, call `ds_verify_agent` to run only the checks preselected by Codex. Poll the same verification job when it is running; do not request `rerun` merely to read its result. Inspect does not execute checks. Read the current patch-bound evidence and actual diff, compare instruction acknowledgements, and examine relevant surrounding code. Actual check success is evidence, not Codex acceptance; stale, unavailable, failed, timed-out or cancelled verification is not a pass.
4. Review the whole scoped change before sending one batch of concrete issues, evidence and expected behavior. Use the same worker for at most two review correction rounds. Worker self-tests and routine compile/format fixes should not each cause a queen round trip. Never weaken an acceptance criterion just to finish a round.
5. If two review correction rounds still fail, Codex takes over the remaining repair. Interrupt the worker, cancel any verification and confirm it has stopped before editing the shared files. Do not infer stopped status from an abort acknowledgement alone. Preserve its patch and include all takeover work in the delegated route's accounting. Do not silently change the selected worker model.
6. Preserve and apply the reviewed patch, then close the agent. Remove its worktree only after useful changes are preserved. Codex owns `/goal` completion after review and validation.

Use `ds_inspect_agent` with `detail="full"` only for missing/truncated evidence, errors, instruction acknowledgements or a specific diagnosis; `include_diff=true` explicitly requests the diff. Never echo large logs into queen messages just to summarize them again. Do not infer success from idle, a timeout or unavailable usage.

Neither native Luna nor an OpenCode worker may commit, push, merge, deploy, modify production data, expose secrets or discard unrelated edits without the user's authorization for that action. If the selected lane is unavailable, report the limitation and continue locally when authorized; do not silently route to the other lane.

## Measure the intended outcome

Optimize high-quality-model consumption while preserving design and review quality. Report Codex controller, native Luna, and external worker usage separately when those counters are available. When measuring, distinguish planning, coordination, review and takeover phases; include failed attempts and all correction rounds. API list pricing does not establish Codex subscription or quota consumption. Codex noncached input plus output is a useful proxy, not a subscription-quota or billing conversion. Keep lane/model/effort unchanged when testing the workflow. Tiny tasks may route directly and must be reported as direct.

Benchmark or live inference runs require the user's task to include them. Do not start extra comparisons merely to validate a Skill update. Local mocked/unit checks are sufficient to report implementation correctness; they do not prove token savings.

Read [control contract](references/control-contract.md) when instruction routing, cursor recovery, workspace modes or a lifecycle edge case needs clarification. It is not required reading on every ordinary delegation.
